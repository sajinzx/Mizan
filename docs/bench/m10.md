# M10 optimizations: before and after, 2026-10-12

Only one of the three optimizations measurably helped:
- **State root v2** is 9.6× faster per block at 10,000 accounts and 70× faster at 100,000.
- **The intrusive price levels** did not show a clear win on this laptop.
- **Ed25519 key reuse** gave nothing measurable.

Every number comes from the raw JMH output in [`raw/2026-10-12-m10/`](raw/2026-10-12-m10/) (JSON plus the human-readable logs).

**Method.**
- Same machine and settings as the [M3 baseline](baseline.md): Ryzen 7 4700U laptop on AC power, 7.4 GiB RAM, Windows 11, JDK 21.0.12.1, 2 forks × (3 × 2 s warm-up + 5 × 2 s measurement).
- **Before** is the pre-M10 commit `fcd990f` built in a separate worktree, with the new benchmark harness copied in (`before-*`). **After** is `62b5339` (`after-*`).
- Runs took turns on one idle machine; no core pinning and no frequency control.

**How much to trust a difference.** Two runs of the same code with the same default collector gave 2.75 ± 0.79 and 3.46 ± 0.32 M commands/s (`after-ExecuteBench`, `gc-G1`). On this laptop, differences below about 25% are within run-to-run noise.

## 1. Intrusive price levels + primitive order index (M10-T1)

`BookBench`, throughput in M ops/s. `depth` is price levels per side; `perLevel` is resting orders per level. `perLevel = 64` is a deep FIFO queue, where the old `ArrayDeque` scan on cancel matters most.

| Operation | depth | perLevel | Before | After | Change |
|---|---|---|---|---|---|
| addCancel | 10 | 4 | 13.0 ± 3.1 | 12.7 ± 1.0 | ≈ 0 (noise) |
| addCancel | 10 | 64 | 8.55 ± 1.63 | 10.75 ± 0.31 | **+26%** |
| addCancel | 100 | 4 | 13.3 ± 1.3 | 9.5 ± 1.3 | −29% |
| addCancel | 100 | 64 | 8.39 ± 0.79 | 9.09 ± 0.37 | +8% (noise) |
| addCancel | 1000 | 4 | 7.68 ± 0.18 | 6.17 ± 0.45 | −20% |
| addCancel | 1000 | 64 | 4.87 ± 0.52 | 3.90 ± 0.46 | −20% |
| matchOne | 10 | 4 | 40.6 ± 1.6 | 38.0 ± 0.9 | −6% |
| matchOne | 1000 | 64 | 34.2 ± 1.3 | 32.4 ± 2.8 | ≈ 0 (noise) |

**Reading.** Cancel is O(1) now (`PriceLevelTest.intrusiveUnlinkAnywhere`), and the one configuration built to expose the old scan (shallow book, 64-deep queue) improved by 26%. Everywhere else the `TreeMap` lookup of the price level dominates. The new `Long2ObjectHashMap` index and the dirty-key hooks added for state root v2 did not pay off measurably here; some rows got slower, by about the size of the noise.

**Verdict:** kept for its O(1) worst case. It is not counted as a throughput win.

## 2. State root v2: sparse Merkle tree, dirty-key batching (M10-T2, ADR 0016)

`StateRootBench`: one operation is a block of 100 deposits to random accounts followed by `stateRoot()`. Mean in µs per block, with p99 from the SampleTime run.

| Accounts | v1 full recompute | v2 incremental | Change |
|---|---|---|---|
| 100 | 104 | 364 | **3.5× slower** |
| 1,000 | 721 | 599 | 1.2× faster |
| 10,000 | 8,255 | 860 | **9.6× faster** |
| 100,000 | 80,086 | 1,145 | **70× faster** |

**Reading.** v1 grows linearly with state. v2 grows with the number of keys changed and the tree depth, so it hardly grows with account count. Below about 1,000 accounts, v1's single pass over a small state is cheaper than 64-level paths.

**Verdict:** the clear win of M10. It is the default in the sandbox genesis and opt-in elsewhere, because v1 is still the default `stateRootVersion`.

## 3. Ed25519 verifier: cached decoded keys, per-thread `Signature` (M10-T4)

`VerifyBench`, µs per signature (SampleTime).

| Path | Before p50 / mean | After p50 / mean |
|---|---|---|
| `plain` (no cache) | 849 / 893 | 886 / 948 |
| `cachedHit` (`CachingVerifier`, already verified) | 0.40 / 0.46 | 0.40 / 0.56 |
| `batchVirtualThreads` (256 at once, 8 hardware threads) | 0.005 ops/µs ≈ 5,000/s | 0.006 ops/µs ≈ 6,000/s |

**Reading.** Decoding the key and looking up the provider are negligible next to the pure-Java curve arithmetic, so reuse gives nothing measurable. What matters is architectural:
- the `CachingVerifier` makes the engine's re-verification of a pre-checked command about 2,000× cheaper (0.5 µs instead of about 900 µs);
- spreading verification over virtual threads gives about 6× the throughput of one thread, on 8 hardware threads.

**Verdict:** no win. The code stays because it is simpler, not because it is faster.

## 4. Garbage collectors (M10-T3)

`ExecuteBench` with signatures off, each collector in its own run with `-Xmx1g`. Latency in µs per command; `max` is the largest observed sample, not a bound.

| Collector | Throughput (M cmds/s) | p50 | p99 | p99.9 | max (observed) |
|---|---|---|---|---|---|
| Parallel | **3.74 ± 0.04** | 0.20 | 0.90 | **6.8** | 885 |
| G1 (default) | 3.46 ± 0.32 | 0.30 | 0.90 | 8.4 | 1,161 |
| Shenandoah | 2.95 ± 0.57 | 0.30 | 1.30 | 39.0 | 5,456 |
| ZGC (generational) | 2.60 ± 0.81 | 0.30 | 1.20 | 40.1 | 21,070 |

**Reading.** The engine allocates 251 bytes per command (`alloc.txt`, `gc.alloc.rate.norm`), all short-lived. Young-generation copying collectors (Parallel, G1) handle that at the lowest cost. The concurrent collectors pay barrier costs on every access and show worse tails here, not better: their advantage is large heaps, which this benchmark does not have.

**Verdict:** keep G1, the default. Use Parallel for a throughput-only batch replay.

## 5. Object pooling (M10-T5, conditional): not done

The condition was allocation pressure in the profile. At 251 B per command and 3.5 M commands/s the engine allocates about 0.9 GB/s, and G1 keeps p99.9 at 8.4 µs. Pooling `Order`/`Trade` would put mutable objects behind the immutable `Trade` records that listeners keep. There is no measured problem to justify that, so it is skipped.

## 6. Undo journal and group commit (M10-T6, optional): not done

Cut, following the spec's cut order. `copy()` is now O(state) only for the book and ledger: the v2 trees are shared persistently. Block-log fsync is one per block by design (ADR 0002).

./gradlew :mizan-bench:jmh -Pjmh.includes=ExecuteBench -Pjmh.params=signatures=off -Pjmh.profilers=gc -Pjmh.results=alloc
