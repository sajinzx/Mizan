# ADR 0015: Rotation via a gossiped command pool; optimistic execution only in proposals

**Context.** M8 asks for proposer rotation, command forwarding to the current proposer, optimistic execution only on the current proposer (with `REVOKE` on losing the role), block sync, and heartbeats. Keeping a per-node sequencer pipeline (speculative core + drafts) while the proposer changes every height would mean re-seeding the speculative core on almost every block, and racing drafts against role changes.

**Decision.**
- **Gossip instead of point-to-point forwarding.** Every validator's gateway puts accepted commands in its `CommandPool` and gossips them (`TX`) to all validators. Each validator re-gossips its own clients' commands every ~2 s until they commit. Whoever is proposer at `(h, r)` therefore already has the commands. Proposer changes and lost forwards need no special handling. De-duplication by `(account, nonce)` makes repeated forwarding idempotent.
- **Optimistic execution only at proposal time.** The proposer executes the head of its pool on a copy of the committed core when it proposes: it skips `AUTH_FAILED` commands (defect 1), computes the root, and sends provisional results to *its own* clients. That copy is its speculative state for exactly one proposal. If a different block is decided, it emits `REVOKE(firstTradeSeq of its proposal)`. Non-proposers never execute optimistically.
- **Final data comes from decided blocks.** Every validator commits every block. It answers `FINAL` to its own clients, and replays the engine events recorded during validation (committed trades and depth) to its gateway and market data, so no block is executed twice.
- **Sync inside the consensus channel.** `SYNC_REQ(fromHeight, max ≤ 64)` / `SYNC_RESP(blocks)`. Each block is checked like a `COMMIT`: structure, a certificate with 2f+1 distinct valid signatures, and a sync-mode replay with root check. A peer that serves an invalid block is ignored for 60 s. Sync is triggered by messages from heights more than one ahead, and by UDP heartbeats `{node, height, head}` every 500 ms. Heartbeats are advisory only, since certificates are what make sync safe.
- The M7 fixed-proposer path (sequencer + drafts on validator 0) stays available as `mizan cluster --fixed-proposer`. The single-node and in-memory modes keep the sequencer pipeline.

**Consequences.** In rotating mode a client's provisional ack arrives only if its own validator proposes the block. Otherwise the first answer is `FINAL`, which the client protocol already allows. Throughput is bounded by consensus latency rather than by the sequencer pipeline (no pipelining across heights in this mode).
